# 文件 checkpoint 与整轮回滚设计

日期：2026-10-05

目标工作树：`tx:/home/pl/.config/superpowers/worktrees/deer_mini/checkpoint`，分支 `checkpoint`。

## 1. 已确认的方案

每轮对话开始前保存一个恢复点，包含当时的 ThreadState 和文件清单。文件内容按 SHA-256 去重保存；未改变的文件由多个恢复点共用同一个内容对象，不重复复制整个目录。

第一版恢复粒度为整轮：选择某轮后，恢复到该轮用户消息加入之前的消息状态和文件状态。原 Run、事件与 checkpoint 继续保留作为历史记录。下一轮从恢复后的状态执行。

覆盖当前 Thread 的 uploads、workspace、outputs 中的普通文件和目录，包含二进制文件、新增、修改、删除、重命名和空目录。之后上传的文件也会被撤销，恢复预览明确展示这些变化。Bash 和子任务修改这些目录中的文件，同样纳入恢复范围。

恢复不撤销容器其他目录、进程内存、外部 API、外部数据库或用户级长期记忆。放在三个目录里的虚拟环境按普通文件处理，没有隐式排除；代价超过容量上限时明确失败。恢复需要重建 Bash 容器，因此不承诺保留或还原容器内已安装的环境。

## 2. 当前代码与需要补齐的边界

- `CheckpointRepository` 保存完整 ThreadState，但没有保存文件。`latest()` 按时间寻找最后一条记录，不能表示恢复后的当前状态。
- `AgentRuntime.run()` 在首次保存前已经追加本轮用户消息。需要新增追加消息之前的 `turn_start` 恢复点；工具调用后的执行 checkpoint 保持原有用途，不逐次生成文件快照。
- `ThreadPaths` 管理三个文件区域和路径边界，继续作为文件定位入口。
- `WorkspaceFileService` 可以独立接收上传，目前没有与 Run、快照、恢复共用的协调机制。
- `ThreadSandboxManager.end_run()` 保留运行中的空闲容器。快照前和恢复前必须停止当前 Thread 的残留容器，不能把正常归还视为停止后台进程。
- `workspace/.tool-results` 保存消息引用的工具结果，属于应用历史资料，需要单独保护，不能随恢复删除。

## 3. 方案取舍

采用完整文件清单加文件级内容去重：可以覆盖 Bash 的任意文件修改，不依赖工具操作日志，恢复目标明确。

不采用仅在编辑工具执行前备份：它无法完整覆盖 Bash、脚本的间接写入和子任务修改。

不采用项目 Git 记录文件版本：三个区域包含上传、图片和 PDF，需要精确覆盖文件存在性和目录；独立备份库也避免干扰开发仓库、Git 索引与忽略规则。

第一版不做文件内部的分块去重、压缩、全局跨用户共享或文件系统快照。一个大文件改变后，保存它的完整新版本。

## 4. 存储格式

备份库位于当前 Thread 目录下独立的 `.checkpoints/`，不挂载进 Bash，不暴露给模型文件工具或普通文件下载接口。目录权限 0700，内容文件权限 0600。Thread 删除时一起清理。备份内容和运行数据不能加入 Git。

```text
thread/
  uploads/
  workspace/
  outputs/
  .checkpoints/
    objects/<sha256前两位>/<sha256其余部分>
    staging/<operation_id>/
```

清单保存在 SQLite 的快照记录内，包含 schema_version、三个根目录和按路径排序的条目。文件条目包含区域相对路径、类型、sha256、字节数和普通权限位；目录条目记录路径和普通权限位，保留空目录。不存在于清单中的用户文件，在恢复时删除。

不保存宿主用户/组身份、setuid/setgid 位、ACL、扩展属性或精确时间戳；不承诺这些元数据的恢复。恢复普通权限位时去除特殊权限位。

对象通过临时文件写入，边读边计算哈希，flush/fsync 后原子移入对象路径并同步目录。备份对象与工作文件不使用硬链接，避免后续原地写入污染备份。恢复也不能直接把可写工作文件链接到对象库。

文件和目录条目合计默认最多 50,000 个，单份清单默认最多 16 MiB，均可配置；备份字节数按第 9 节限制并逐步检查，避免一次性读取大文件。哈希计算和磁盘操作在线程中执行，不阻塞 FastAPI 事件循环。第一版每轮扫描并读取全部普通文件，不仅根据 mtime/size 判定是否变化；内容去重节省存储，但不消除扫描耗时。

## 5. 数据库与当前状态

新增文件快照记录和恢复点记录：

- 文件快照：id、thread_id、清单、内容总字节数、创建时间。
- 恢复点：id、thread_id、run_id（恢复备份可为空）、state_checkpoint_id、file_snapshot_id、类型（turn_start/recovery）、创建时间、可用状态。
- Thread 当前状态指针：thread_id、checkpoint_id、revision。正常保存执行 checkpoint 时，在同一数据库事务中推进指针；恢复时切换到新的恢复 checkpoint。
- 恢复操作记录：operation_id、thread_id、目标恢复点、恢复前恢复点、expected_revision、状态（prepared/applying/committed/rolled_back/needs_recovery）、错误分类与时间。

checkpoint 增加内部类型，区分 execution、turn_start、restore；原有数据默认为 execution。恢复生成新 checkpoint，而非删除旧记录。恢复 checkpoint 使用目标状态 checkpoint 的 Run 作为外键，并分配新的唯一 step；recovery 恢复点没有独立 Run 时同样沿用其状态 checkpoint 的 Run。按 Run 的执行状态和 SSE 恢复查询只取 execution，不能把 restore 当成该 Run 的新执行结果。

升级时从原 `latest()` 初始化 Thread 当前指针。已有 Thread 没有文件备份的旧轮次显示不可恢复文件，不能补造过去的文件内容。保留现有成功响应结构；新增恢复点、预览、恢复操作接口，前后端类型一起更新。

## 6. 执行协调与快照时机

增加按用户与 Thread 索引的操作协调器，统一管理 Run 预约、上传、快照、恢复和 Thread 删除。恢复优先登记独占状态后才能取消活动 Run，防止等待取消期间插入新 Run。

锁分为外层操作准入与短时文件独占，取消与 Run 收尾不在持有它们需要的互斥锁时等待，避免死锁。快照过程中阻止文件写入、上传及 Thread 删除；Run 的工具和子任务在快照提交后才准入。上传在活动 Run 期间返回冲突，前端提示等待结束，避免附件内容在执行期间被替换。

每轮开始流程：

1. 验证用户归属并预约当前 Thread，拒绝恢复中或尚待恢复的 Thread。
2. 停止并移除当前 Thread 的旧 Bash 容器，确认后台进程不再写挂载目录；失败则不运行模型。
3. 加载当前指针指向的 ThreadState（首轮为空状态），在追加用户消息前扫描文件并落盘内容对象。
4. 在同一 SQLite 事务保存 turn_start 状态 checkpoint、文件清单和恢复点关联。
5. 确认持久化成功后，追加用户消息，保存原有执行 checkpoint，启动 Run 和新容器。
6. 工具调用后仍按现有规则保存消息/任务状态，不重复扫描目录。Run 结束后停止该 Thread 容器，等待执行和写入完全结束，再开放上传及下一轮。

备份失败、目录不支持、容量不足或容器停止无法确认时，Run 明确失败且模型/工具不执行；不得静默跳过文件后标记恢复点可用。现有错误和取消边界保持：不吞 CancelledError、StatePersistenceError，不重放已经执行的工具。

这个功能启用后，关闭跨轮容器复用，接受每轮容器启动成本，换取文件快照的一致性；不进行环境快照。服务外手工写宿主目录无法由应用锁协调，不承诺在这种并发写入下得到一致快照。扫描检测到条目变化时应失败，不能保存混合版本。

## 7. 路径与历史结果

遍历不跟随符号链接，使用 ThreadPaths 的区域边界校验。遇到符号链接、硬链接或 FIFO/socket/device 等不支持条目时，明确失败，不静默跳过，也不读写链接指向的位置。读取时校验文件身份与读取前后状态，采用不跟随链接的打开方式防止校验后替换。停止应用写入仍是主要的一致性前提。

`workspace/.tool-results` 是明确的保留区域，不进入用户文件恢复清单，不计入文件快照容量；其原有结果存储策略不在本次优化范围。Docker 为该目录添加嵌套只读挂载，应用仍可从宿主写入新的结果。既有路径含链接时拒绝挂载，不绕过边界。恢复保留该目录；更旧 checkpoint 与历史 Run 的结果链接保持可用。普通模型写入工具也不得修改这个保留目录。

当目标清单要求用文件覆盖该保留目录或其祖先时，拒绝恢复。清单不能引用保留目录中的用户对象，也不能包含 `.checkpoints`、绝对路径或 `..`。

## 8. 恢复流程与失败恢复

用户先看到新增、覆盖、删除的预览，包括后续上传文件。预览返回 Thread revision 与当前文件状态指纹；恢复请求携带两者，文件或状态变化时返回冲突并要求刷新预览，不覆盖预览之后的新上传。

恢复流程：

1. 验证 Thread、恢复点归属和请求版本，登记独占恢复状态。
2. 如有活动 Run，执行取消并等待所有工具、子任务和持久化收尾；停止当前 Thread 的活动和空闲容器。取消或停止无法确认时不改文件。
3. 重新确认预览有效；验证目标清单和每个对象哈希。保存当前消息与文件作为 recovery 恢复点，供失败恢复及撤销本次恢复使用。
4. 在同一文件系统 staging 构建目标三个目录并检查空间。保留 `.tool-results` 的位置与内容。
5. 持久化 prepared 操作记录，进入 applying。按目录分别交换目标目录与旧目录，每次交换前后同步目录并保存足以判断进度的记录。
6. 文件目标确认完成后，在一个 SQLite 事务内保存 restore checkpoint、推进当前指针和 revision、标记操作 committed。
7. 确认完成后清理临时目录，解除独占，返回恢复成功；前端刷新消息、任务和文件列表，关闭旧预览并清除旧 SSE 缓存。

三个目录交换和 SQLite 提交不是一个原子事务，不能仅凭 os.replace 宣称整体原子。prepared/applying 必须可重放：数据库未 committed 的操作在启动时恢复到 recovery 状态；已 committed 的操作完成目标验证与临时目录清理。无法确认时标记 needs_recovery，禁用该 Thread 的执行、上传和再次恢复，不报告成功。服务启动先恢复这些操作，再开放 API。

恢复期间普通文件列表/下载返回冲突，避免看到混合状态；内部恢复读取不经过对外接口。重复请求通过 operation_id 查询已有操作，不重新执行恢复。取消 HTTP 请求不能中断已开始的持久化恢复收尾；进程崩溃由操作记录恢复。

recovery 恢复点使用相同的恢复机制，可撤销本次回滚。恢复不会修改旧 Run 的终态。用户级记忆与已完成的记忆更新保留，界面明确说明；后台记忆任务不能推进 Thread 当前状态指针。

## 9. 保留策略和容量

初始默认值：每个 Thread 保留最近 100 个用户可选恢复点，去重后的备份内容对象与清单合计上限 1 GiB；通过后端配置调整。recovery 恢复点也计入保留数与容量。

目标恢复点、进行中的恢复操作引用、最近一次恢复的 recovery 点暂时固定，不能被清理。成功建立新的恢复前备份后，可解除更早 recovery 点的固定。当前状态 checkpoint 始终保留。

创建新恢复点之前，按顺序清理未固定的最旧恢复点，再以所有仍存在的恢复点以及尚未完成清理的恢复操作为根遍历引用，删除无引用内容对象。终态操作完成清理后不再固定文件快照，仅保留审计编号，避免终态日志阻止回收。仅删除自有备份库对象，不删除工作文件或历史 checkpoint。对象路径存在但未被事务引用的失败写入由下一次清理回收。

容量仍不足时明确阻止本轮或恢复，保留已有有效恢复点，不自动降低覆盖范围。恢复 staging、保留的旧工作目录、对象写入临时文件会产生额外磁盘占用，不由 1 GiB 归档上限自动保证；操作开始前检查可用磁盘，实际 ENOSPC 仍按失败恢复处理。

## 10. 对外接口和界面

新增接口全部使用现有用户归属校验，不由客户端选择宿主路径：

- 列出 Thread 可用恢复点及不可用原因。
- 预览指定恢复点的文件创建、覆盖、删除和消息撤销范围。
- 发起整轮恢复，接受 operation_id、revision 与文件状态指纹。
- 查询恢复操作状态。

恢复列表显示对应用户消息与时间；首轮也有“本轮开始前”入口。第一版只提供消息和文件一起恢复，不做任意工具步骤恢复和文件单独恢复。界面注明三个目录的恢复范围、后续上传可能被撤销、环境和长期记忆不恢复。

恢复成功后，Thread 状态由当前指针读取，原历史 Run 与事件仍可查看。新一轮不会重新加载被撤销轮次的最新旧 checkpoint，不自动重跑旧工具。

## 11. 验收与验证

自动化测试只用临时数据库、临时 Thread 文件目录、mock 模型/容器与测试用户：

- 首轮恢复为空消息状态，已有上传保持在本轮开始前版本。
- 修改、新增、删除、重命名、二进制文件、空目录与普通权限位正确恢复。
- 多个恢复点引用相同内容时只存一个对象；删除部分恢复点不会破坏剩余恢复点。
- Bash/脚本/并行子任务写入在轮次间被完整记录，容器停止失败时拒绝快照与恢复。
- 容量不足、扫描期间文件变化、对象损坏、unsupported link、路径越界与错误归属明确失败。
- 上传、开始 Run、Thread 删除与恢复竞争时不会出现交叉写入或死锁。
- 执行中取消后恢复，不吞掉取消与关键持久化异常。
- 每个目录交换位置、对象写入、SQLite 提交前后的失败与重启恢复；成功响应只在已提交后产生。
- 预览之后上传/状态变化引发冲突；相同 operation_id 重复请求不重复恢复。
- 旧工具结果仍可读取，Bash 无法修改历史结果目录。
- 恢复后继续对话使用目标状态，旧 Run 的 SSE 恢复仍读取该 Run 的 execution checkpoint。
- 前端范围提示、预览、恢复状态、文件列表刷新与旧流缓存清理。

实现完成后运行项目规定的后端回归（排除真实模型测试）以及前端 typecheck、test、build。文档阶段只检查内容、路径与 diff，不运行无关测试。

## 12. 交付边界

本设计不涉及运行服务、Caddy、线上数据库或线上用户文件的变更。后续实现仅在 checkpoint 工作树及隔离测试数据内进行。提交、推送和部署遵循用户对当前任务的授权。
