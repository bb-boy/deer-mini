# 新增模块开发

本 skill 只约束新增模块开发的需求确认和收尾：通过 GrillMe 形成并确认需求文档，开发完成后由独立 reviewer 对照文档审查并完成修复复审。

开发按照 GrillMe 生成并经用户确认的文档完整实现。主 agent 自行决定任务拆分、实现方法、使用哪些技能以及是否委派 subagent 开发或修复。本 skill 不规定中间开发步骤，也不将文档范围缩减为最小实现。

项目规范以当前仓库和目标目录的 `AGENTS.md` 为准。沿用用户已经确认的决定；参与实现的 subagent 执行主 agent 分配的任务，不重复启动需求访谈；reviewer 独立执行审查。

## 1. 需求确认

- 按 `AGENTS.md` 检查分支、暂存区、工作树差异和未跟踪文件，区分既有工作与本任务。确认真正的源码仓库和执行位置；只有文档的目录不能当作可运行的源码基线。
- 先查代码能回答的问题，再使用已安装的 `engineering-suite-grill-me:entry-grill-me`，按其入口路由读取插件内的需求梳理技能。通过当前技能目录发现依赖，不写死插件缓存的版本路径。缺少 GrillMe 时说明缺项，请用户选择补齐依赖或改用普通需求梳理，不假称已调用。
- 聚焦模块目标、用户行为、边界、接口、失败路径和验收标准。已有确认过的需求时只梳理缺口，不重做访谈。GrillMe 负责需求阶段，之后由主 agent 组织开发。
- GrillMe 生成的需求、设计文档及相关决定统一放在实际源码主仓库根目录的 `docs/` 下，可按模块建立子目录；调用 GrillMe 时明确传入此输出位置。记录当前任务文档的绝对路径，交由用户确认；已有确认无需重复询问。收尾以这些文档及用户后续确认的变更为验收依据。只有影响正确性或范围的未决问题才阻止对应实现，独立工作可以继续。
- 需求确认后，在实际源码主仓库根目录的 `.worktree/<模块名>/` 创建或复用本任务的隔离工作树；目录名使用单数 `.worktree`，不改用其他默认位置。先确认 `/.worktree/` 已被 Git 忽略，缺失时补入项目 `.gitignore`。核实源码基线，记录工作树路径和模块起始提交 SHA。让主 agent、开发 subagent 和 reviewer 都能读取同一确认版本的 `docs/` 文档及项目规则，保留已有未提交工作。之后的开发安排由主 agent 决定。

## 2. 收尾

### 核对文档和验证结果

- 对照 GrillMe 文档及用户确认的变更，逐项核对实现和验收标准，检查完整任务差异。
- 按项目规范完成与改动相关的验证，记录命令、结果和对应代码状态。环境不足、未执行、历史失败与本次失败分别说明。
- 收尾必须完成独立 review，无论代码由主 agent 还是开发 subagent 实现。使用未参与该改动实现的 reviewer，不以实现者自查替代独立审查。

### 派发独立 review

读取 [reviewer 配置](../../../.codex/agents/deer-mini-module-reviewer.toml)。它参考 `Requesting Code Review` 和配套的 `Code Review Agent`，包含审查标准与输出格式；本节负责派发和闭环。

- 优先使用当前运行环境实际支持的自定义角色派发方式选择 `deer-mini-module-reviewer`。若工具不支持按角色名选择，显式读取该 TOML 的 `developer_instructions`，作为角色指令传给独立子 agent；不要编造 `agent_type` 等当前工具没有的参数，也不要声称配置已自动加载。
- 使用新上下文，不继承主 agent 或开发 subagent 的完整会话；在当前 `collaboration.spawn_agent` 接口中使用 `fork_turns="none"`。不指定模型覆盖，除非用户或适用配置明确要求。提供用户的相关指示和必要的项目规则。
- 如果没有可用子 agent，说明独立审查尚未完成；可以继续自查，但不能把自查记作独立 review。

每次派发都附上这些实际材料，不发送未填写的占位符：

| 材料 | 内容 |
| --- | --- |
| 实现与需求 | 实现范围、GrillMe 生成且用户确认的文档、验收标准及后续确认的变更 |
| 执行位置 | 工作树绝对路径、根目录及相关子目录的 `AGENTS.md` |
| 提交范围 | 经核实的模块起始 `BASE_SHA`、当前 `HEAD_SHA`，覆盖整个模块的提交 |
| 未提交改动 | 暂存与未暂存差异、属于本任务的未跟踪文件清单及可读取内容 |
| 验证与边界 | 测试命令、结果、未验证事项和用户相关指示；不加入诱导通过的结论 |

`BASE_SHA..HEAD_SHA` 只覆盖提交，不能代替整个工作树。不要默认用 `HEAD~1` 作为模块基线。让 reviewer 在同一工作树读取全部任务改动及必要的关联代码；审查期间保持该范围稳定，发生变化就更新审查材料并检查受影响部分。检查范围可以跨模块以验证集成，修改范围仍受需求约束。

一次覆盖相同范围的独立 review 可以同时满足 `Requesting Code Review` 等适用技能的审查要求，不重复派发。等待实际结果，不能把启动 reviewer 当作审查完成。

### 修复、复测和交付

- **Critical**：立即核实并修复，阻止完成声明。**Important**：交付前解决；用户明确接受例外时记录影响，不能悄悄降级。**Minor**：按范围决定是否处理，保留必要说明。
- 主 agent 根据文档、代码和测试组织核实每条意见；reviewer 判断有误时给出证据，不盲从。修复可以由主 agent 自行完成或委派开发 subagent，reviewer 保持独立，不直接改源代码。
- 修复后运行相关检查，并让 reviewer 检查修复及其影响；新增实质改动也需要审查。重复争议先核对需求和证据，只有需要产品取舍或需求变更时请用户决定，不无限循环改代码。
- 最终条件：GrillMe 文档和用户确认的变更得到落实，验收项有实现和验证依据，最终代码已被审查，阻塞问题已解决或由用户明确接受，未验证事项如实列明。若已有计划，同步状态和遗留项。
- 交付说明包含文档落实情况、改动、工作树/分支、验证结果、review 结论和未完成事项。Git 操作、部署及工作树清理遵循用户指示和项目规范。
