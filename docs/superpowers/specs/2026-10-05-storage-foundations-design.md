# 公共存储处理与记忆保存恢复设计

日期：2026-10-05。状态：用户已于 2026-10-05 授权开发；实现位于 storage-foundations 隔离分支，完整后端回归通过；未合并、未部署。

本设计依据 GrillMe 访谈中已确定的选择。业务词汇见 `CONTEXT.md`，核心取舍见 `docs/adr/0001-memory-save-recovery-boundary.md` 和 `docs/adr/0002-memory-save-task-records-in-sqlite.md`。文中的接口、字段及状态名称是建议的工程表达，最终实现需满足这里约定的行为。

## 1. 目标与范围

优先统一存储失败的表达：失败发生在哪一步、是否可能已经写入、上层应如何处理。同时复用文件读写能力，并让已经登记的记忆保存任务能够跨服务重启恢复。

| 范围 | 本次约定 |
| --- | --- |
| 公共文件读写 | 提供安全读取、原子替换、流式上传所需的可复用能力，保留各业务的路径与大小限制 |
| SQLite | 保留现有 Repository，使用共同的存储错误分类，不改成通用文件写入接口 |
| 持久恢复 | 第一版仅覆盖已校验并确认登记的记忆保存任务 |
| 主执行 | Checkpoint、工具结果等关键持久化失败仍按现有 Runtime 边界传播 |
| 观察与管理 | 结构化后台日志、SQLite 任务记录、后台管理命令 |
| 前端 | 聊天界面不展示记忆状态，不新增记忆任务管理 API 或 SSE 事件 |

不扩大为所有 IO 的通用任务队列，不承诺抽取未完成或登记未确认的记忆能跨重启恢复。模型输出 JSON、字段和原话引用的校验与修正属于抽取层；本设计不会通过重新调用模型解决文件写入失败。

## 2. 当前代码事实

- SQLite 保存对话消息、Checkpoint、Run 和事件；Checkpoint 的完整状态是恢复对话的依据，事件不是完整对话快照。
- 记忆正文和索引使用文件；工具结果和附件也使用文件，但写入方式与安全约束有差异。
- 记忆、工具结果已有临时文件、文件同步、原子替换及目录同步处理；上传已有流式大小限制和原子替换，但尚无相同的目录同步步骤。
- `runtime/async_io.py` 处理异步取消与正在进行的同步操作，不是公共存储模块。
- 现有记忆任务保存在进程内，服务重启后不能恢复；队列结束也不能证明每条记忆已保存。
- 现有记忆保存先写正文再写索引，两者不是一个事务；读取索引时可能根据正文重建索引。

以上是现状，后续各节描述拟增加的行为。设计继续遵守单进程运行条件。

## 3. 分层职责

```text
业务调用方（Runtime / 记忆服务 / 工具中间件 / 上传服务）
    │ 解释业务后果，决定降级、终止或恢复
    ▼
业务存储（MemoryStore / 各 SQLite Repository / 文件服务）
    │ 保留领域规则、所有权和路径隔离
    ▼
公共文件 IO 能力 + 共同 StorageError 约定
    │ 报告技术原因、失败阶段、提交是否确定
    ▼
文件系统 / SQLite
```

公共层报告“替换已经发生，但目录同步失败”；记忆层解释为“保存结果待核实”，Runtime 可以解释为“关键状态持久化未确认”。公共层不决定 Run 是否成功，也不自行启动模型或后台任务。

公共文件能力必须支持有边界的读取、原子写入，以及上传的流式写入；不能用不受约束的 `Path.read_text()`、`Path.write_text()` 替换当前实现。Thread 文件使用 Thread 的路径解析，用户记忆使用用户记忆目录的安全规则，不能混用根目录。

## 4. 存储错误约定

建议定义共同的 `StorageError`，携带可以安全记录的字段：存储类型、操作类型、错误分类、失败阶段、提交状态和恢复类别。保留异常原因链供内部诊断，不把完整异常正文、用户记忆内容、凭据或提供商响应直接写入日志。

| 维度 | 建议含义 |
| --- | --- |
| 存储类型 | 文件或 SQLite |
| 操作类型 | 读、写、替换、同步、提交、删除 |
| 技术分类 | 不存在、权限不足、空间不足、暂时繁忙、损坏、IO 故障、非法访问 |
| 失败阶段 | 打开、读写、文件同步、替换、目录同步、数据库事务提交等 |
| 提交状态 | 确认未提交、确认已提交、结果不确定；多项业务另行记录部分成功 |
| 恢复类别 | 可短暂重试、需等待环境恢复、需人工处理、需先核实结果 |

“文件存在”不等于“本次修改已确认保存”。替换后的同步失败、数据库提交时的异常，都可能需要核实实际状态。只有写入所需的持久化步骤确认完成，才能报告保存成功。

预期的“记录不存在”可以由业务接口返回空值；损坏、权限不足和 IO 故障不能一起伪装成不存在。非法路径、越界访问、输入超限仍按业务安全规则拒绝。

`asyncio.CancelledError` 继续传播，不被包装成普通存储错误。`StatePersistenceError` 保留为关键状态失败的上层异常，可携带底层存储原因；不改成普通工具错误或成功结果。

## 5. 上层处理策略

| 场景 | 行为 |
| --- | --- |
| 暂时繁忙、明确未提交的短暂故障 | 允许有总次数和时间预算的有限重试 |
| 空间不足、权限等环境故障 | 已登记的记忆任务延后尝试并记录原因；不得快速循环重试 |
| 提交结果不确定 | 先核实文件或数据库实际结果，再决定继续保存或确认完成 |
| 非法路径、未经校验的内容、保存冲突 | 拒绝自动写入；冲突等待人工处理 |
| 记忆正文损坏 | 保留原文件、记录错误并跳过该条，其他正常记忆继续使用 |
| 记忆索引损坏 | 从健康正文重建；重建写入失败必须可观察，不能宣称修复完成 |
| 关键 Checkpoint 或工具结果保存失败 | 按现有边界传播 `StatePersistenceError`，不报告主执行成功 |
| 辅助事件保存失败 | 保留其辅助性质和有限重试边界，不用它替代 Checkpoint 的成功判断 |
| 普通附件写入失败 | 返回明确失败，保持既有大小和路径错误语义，不加入记忆恢复队列 |

原始存储分类和业务错误可以不同：同一“空间不足”，在记忆后台任务中意味着等待恢复，在关键快照保存中意味着本次主执行不能确认成功。

重试应由适合该业务的上层统一预算，避免公共 IO 重试、任务重试、模型重试层层相乘。保存阶段重试不重新抽取记忆，也不重放已经执行的工具。

## 6. 记忆任务的登记与恢复边界

```text
主 Run 完成并确认关键状态保存
    → 后台抽取记忆
    → 全部候选变更通过校验
    → SQLite 原子登记任务及保存项（确认提交）
    → 调度保存
    → 按项记录结果 / 延后恢复 / 冲突 / 失败
```

跨重启保证从 SQLite 登记确认成功开始。抽取、校验失败不产生可执行保存任务；登记失败明确记录，不能把只存在内存里的任务称为可恢复任务。主 Run 已确认成功后，后台记忆登记失败不追溯改写主 Run 的结果。

这不保证每个成功 Run 都一定完成抽取：主 Run 结束到登记确认之间仍可能发生中断。本次没有选择覆盖这一窗口的全链路恢复设计。

任务按用户隔离，沿用 `user`、`feedback`、`reference` 三类记忆，不新增 `project` 分类。记忆的检索和模型选择方式不在本次变更范围内。

## 7. 持久任务数据

任务、保存项及尝试历史存入现有 SQLite 的新增表；记忆正文继续使用文件。建议的数据职责如下，具体表名在实现计划中确定。

| 记录 | 需要表达的内容 |
| --- | --- |
| 任务 | 稳定任务 ID、用户、来源 Thread/Run 标识、登记时间、当前恢复截止时间、状态、取消请求、关闭时间 |
| 保存项 | 稳定操作 ID、固定新记忆 ID 或更新目标、已校验的变更内容、预期旧版本、预期结果摘要、阶段、状态、下次尝试时间 |
| 尝试历史 | 尝试时间、恢复窗口批次、结果、安全的错误分类与阶段；不复制记忆正文或原话到错误日志 |

一次登记应在同一事务中保存完整任务与各保存项，成功后才交给调度器。来源 Thread 删除不得级联删除任务历史；来源标识需支持对话删除后的查询和取消记录。

SQLite 与文件不是同一个事务。不能仅凭任务记录仍为“处理中”就认为正文未写入，也不能仅凭文件存在就把任务标成成功。

## 8. 每项保存、重复执行与冲突

一次任务允许部分成功。成功项不回滚，恢复只处理未完成项，并保留各项结果。

为避免重复执行造成重复记忆，登记时为每项分配稳定的操作身份；新增记忆 ID 固定下来，更新项保存其依据的旧版本。实现必须提供可靠的版本比较和操作核实机制，不仅依赖随机新 ID 或内容模糊去重。

更新检查与实际写入必须在同一用户的写入保护范围内完成。如果当前记忆仍是预期旧版本，可以继续；如果已是本项确认写入的结果，核实并补齐未完成的索引或任务记录；如果已被其他操作更新，标记冲突，禁止覆盖较新的内容。

关键恢复案例：

1. 正文未替换：原内容保留，可以按规则恢复保存。
2. 正文已保存，索引失败：依据正文与操作身份核实，补齐索引，不再次新增记忆。
3. 文件已保存，SQLite 结果登记失败：重启后核对实际文件，确认结果后补记状态。
4. 文件结果或持久化仍不确定：保持待核实状态，不猜测成功，不盲目重写。
5. 同一目标后来被更新：旧项进入冲突；其他不相关项可以继续。

正文和索引不是原子批次，公开行为按项报告。新增版本或操作来源信息应兼容旧记忆文件，正常加载不能破坏现有内容。记忆最后更新时间反映实际生效的内容更新；核实已完成操作、重建索引和重试空操作不重复刷新时间，继续保留“最后内容更新满 48 小时为 stable”的既有规则。

## 9. 调度、时间与取消

自动恢复窗口默认 24 小时，从确认登记成功开始，包含排队时间。使用持久化的绝对截止时间；重启不延长窗口，已过期任务不会因重启重新获得 24 小时。

失败后逐渐降低尝试频率，记录下次尝试时间。具体间隔与并发上限是实现参数；必须有限、可配置并使用可测试的时钟，不能超过恢复窗口。窗口结束后停止启动新的自动保存尝试；已经开始的提交仍须完成并核实结果。未完成项标记失败，结果不确定项保留待核实状态和必要内容，供后续核实或人工处理。

同一用户的实际写入需串行保护，但处于退避等待的任务不占用写入位置，不阻塞该用户的新任务。后续任务可能更新相同记忆，因此旧项恢复仍必须检查版本。

服务启动扫描已登记的可恢复任务；上次处于处理中或结果不确定的项先核实结果。普通失败、冲突或已取消项不因扫描而重新开始保存；到期后的核实不授权启动新的自动写入。关闭服务时传播取消、释放客户端；已开始的同步文件提交等待结束并核实，任务状态未记录时由重启恢复核实。

删除来源 Thread 会取消其未完成任务，同时防止仍在抽取的旧任务在删除后登记：登记时检查来源仍存在且属于该用户，并与删除操作协调。已开始的同步提交可能完成，取消不承诺回滚；完成结果需要记录，然后停止后续项。已经保存的用户记忆继续保留。

## 10. 状态与后台管理

保存项需要区分：待处理、处理中、等待恢复、待核实、成功、失败、冲突、取消。任务状态由各项结果归纳，必须能表达部分成功，不能用单个成功布尔值掩盖失败或冲突。任务取消后也应保留已成功项的结果。

第一版提供后台管理命令，实现时再给出可执行入口：

- 列表和详情：按用户范围查询任务、每项状态、窗口、阶段和尝试历史。
- 普通失败重试：恢复符合条件的未完成项，确认操作后开启新的 24 小时窗口，保留原历史。
- 取消：停止未来尝试，保留已保存结果。
- 冲突处理：查看当前结果，选择保留当前记忆并取消旧保存项；不提供强制覆盖旧内容的命令。

普通重试不能绕过冲突、非法路径或内容校验。来源 Thread 已删除的取消任务不能重新恢复。命令面向可信后台运维环境，仍须限定用户与任务范围；不宣称当前 `user_id` 检查提供登录或管理员认证。

日志和默认详情只提供必要的安全字段；查看待保存正文需要明确的详情操作，不能把私有内容自动写入日志。

## 11. 内容与历史的保留

任务成功或取消后，清除任务记录中复制的待保存内容；保留任务标识、状态、安全错误信息与尝试历史 30 天。建议从任务确认关闭时起计时；部分完成项可提前清除其重复正文，但保留核实所需的操作标识、摘要和版本信息。

未处理的失败或冲突项保留待保存内容，用于人工判断或重试；其任务不因等待超过 30 天被误删。索引或写入结果仍未核实的项不能提前清除必要信息。

历史清理只处理任务记录，不删除实际用户记忆文件。这里的“清除内容”是应用层删除，不承诺 SQLite、WAL 或备份介质中的物理安全擦除。

## 12. 验收要求

后续实现使用临时数据库、临时文件、故障注入、假模型和可控时钟验证，不连接线上数据库、用户目录或真实模型服务。

1. 读写错误的分类、阶段、提交状态与原因链正确；取消和关键持久化异常按边界传播。
2. 替换前、替换后、文件同步和目录同步失败可区分；不把不确定提交报告为成功。
3. 正文成功但索引失败、文件成功但任务状态失败后，重启能恢复，不重复新增、不刷新已经完成的更新时间。
4. 旧项恢复时遇到新版本进入冲突；同一用户的新任务不被旧任务的退避阻塞。
5. 全部校验成功且登记确认后才具备恢复能力；登记失败不能报告任务已保存。
6. 24 小时从登记计时且跨重启保持；手动重试开启新窗口并保留旧历史。
7. 删除对话、晚到登记和正在进行的提交的竞态符合取消约定；已保存记忆保留。
8. 部分成功仅恢复未完成项；冲突处理不提供旧内容强制覆盖。
9. 成功或取消后的内容清除、30 天历史清理不会删除真实记忆，也不会删除未解决项的必要内容。
10. 损坏正文保留、健康记忆可用、索引重建失败可观察；安全路径、符号链接与硬链接防护、读取上限和上传大小限制不退化。
11. Checkpoint、工具结果、事件和附件保留各自的业务失败边界；聊天界面无记忆状态展示。
