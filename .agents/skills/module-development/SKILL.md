# 模块开发

把明确的需求交付为经过验证的实现。适用于不同项目和技术栈；项目规则、接口和检查命令从目标仓库读取。主 agent 负责需求、分工、集成和交付，开发者负责实现、自测与修复，独立 reviewer 负责审查与复审。

按任务的风险、依赖和协调需要选择流程重量。完整实现确认范围，选择足够简单的方案；不自行缩减验收项，也不扩展成无关重构。本 skill 直接规定职责边界、独立审查和“证据先于完成声明”，不要求先加载另一套开发工作流；不全局强制 TDD，不为每个小任务重建角色或重复审批。

## 1. 选择流程

先读相关代码、项目规则和已有需求，再分类。不要用固定代码行数或文件数代替判断；发现新的接口、状态或风险问题时升级流程。

| 类型 | 判断依据 | 最小充分流程 |
| --- | --- | --- |
| 小改动 | 行为明确、影响局部、风险低，无需跨步骤协调 | 理解 → 实现 → 针对性验证与自查；不写正式 plan，不默认派发子 agent |
| 普通功能 | 边界清晰，有多个验收点，需要整体检查 | 简短设计/清单 → 实现与自测 → 独立 review → 修复复审 → 最终验证 |
| 复杂模块 | 接口重设计、复杂依赖、迁移/兼容、多阶段交付，或多个开发者并行 | 设计与验收 → 正式 plan → 按依赖开发 → 集成 → 整体独立 review → 修复复审 → 最终验证 |

例如修改已确定的 CLI 提示文案，可以直接修改并检查实际输出；为同一服务新增两个可并行的存储适配器，应先记录共同接口、各自文件所有权、依赖和集成验收。很小的权限或事务改动仍可能需要复杂流程。

正式 plan 的用途是保存跨步骤约束和协作合同，包含任务、接口、所有权、依赖、验收与验证方式即可。小改动无需生成设计、计划、审查报告等一整套文档。普通功能与复杂模块需要独立 review；小改动在用户、项目规则或实际风险要求时增加 review。

任务按可验证的交付边界拆分，配置、测试和文档随对应功能一起安排。每项任务说明消费和提供的接口；跨任务的函数签名、字段名、类型、单位及约束使用同一份定义。计划完成后逐项检查验收是否有任务承接、依赖顺序是否成立、上下游接口是否一致；缺口写明，不用“后续完善”代替必要决定。

## 2. 明确需求和基线

- 找到实际源码仓库，读取适用的 `AGENTS.md`、已有设计及项目命令。检查分支、暂存/未暂存差异和未跟踪文件，保留已有工作；文档目录不能被当作源码仓库。
- 已有用户确认的需求、设计或验收标准时直接沿用，不要求它来自特定工具。先用代码回答技术事实，只就影响正确性、范围或产品取舍的实质缺口提问，其他工作继续。

### 何时使用 GrillMe

用户明确要求的流程优先；其余按尚未解决的问题选择。通过当前环境已安装的 GrillMe 入口路由，不写死插件缓存版本，也不要求依次执行全部子流程。

| 当前情况 | 处理方式 |
| --- | --- |
| 受众、要解决的问题或成功标准不明确，无法写出具体目标 | 使用 GrillMe 的 `interview-me` 澄清真实意图 |
| 目标已有方向，但需要探索、比较并收敛多个想法或方案 | 使用 `idea-refine`，明确推荐方向、范围及关键假设 |
| 用户明确要求 grill、质疑或压力测试方案，或存在影响范围、成本、兼容性等关键取舍的未验证假设 | 进入方案追问流程；当前入口在有工作仓库时路由到 `grill-with-docs`，否则使用 `grill-me` |
| 已有确认需求，只有少量局部缺口 | 主 agent 先查代码，再针对缺口简短澄清；若暴露目标或关键方案不确定，再进入上面的对应流程 |
| 需求和验收完整，或只是行为明确的局部修复、文案调整 | 直接沿用已有要求，不因任务开始或恢复而重新访谈 |

技术事实能由代码或文档回答时先调查，不把常规实现选择交给用户。未指定 GrillMe 且它不可用时，主 agent 做等价梳理；用户明确指定使用 GrillMe 时，说明缺失并只暂停依赖它的部分，不自动安装插件。

**结束条件：**目标用户与行为、范围与非目标、关键接口或约束、失败路径、可验证的验收项已明确，影响它们的产品取舍已获用户确认。达到条件就结束梳理，按下面规则保存需求，再进入设计和开发。未决问题明确记录，只阻止依赖该决定的工作；已有确认和授权持续有效，整理成文档、任务派发及常规修复不产生新的确认轮次。

### 是否生成需求文档，以及放在哪里

- **普通功能与复杂模块：**开始实现前必须有书面需求和验收依据。已有文档足够时直接复用；没有时由主 agent 整理并保存需求文档，无论是否调用过 GrillMe。普通功能保持简短，复杂模块按需要补充接口、兼容或迁移约束。
- **小改动：**用户要求足以直接判断结果时，可以引用原始要求，不强制新建需求文档。用户或项目明确要求文档时，按要求生成。
- **GrillMe 的产出与需求文档：**`interview-me` 主要产出确认后的意图，`idea-refine` 可产出想法文档，`grill-with-docs` 会涉及设计决策和术语记录；调用成功不等于需求文档已落盘。主 agent 检查实际产出，补齐开发与 review 所需的需求和验收。已有产出已覆盖这些内容时可直接作为权威需求，不为文件名称再复制一份；设计决策、术语表或实现计划本身不能替代缺失的需求与验收项。
- **保存位置按优先级选择：**用户指定的路径 → 项目 `AGENTS.md` 或已有需求文档约定 → 实际源码主仓库的 `docs/<模块名>/requirements.md`。模块名用简短小写连字符名称，例如主仓库为 `/path/app` 时，CSV 导出需求默认保存到 `/path/app/docs/csv-export/requirements.md`。不默认放到 skill 目录、临时目录或主 agent 当前所在的文档仓库；未定位源码仓库时先定位，不猜测永久路径。
- **已有文档与工作树：**续接任务沿用同一权威文档路径，在原文中补充已确认的实质变更，避免维护多份相互冲突的需求。隔离工作树中的开发者和 reviewer 使用该文档的绝对路径及内容哈希或提交版本；需要复制时核对版本一致。后续需求变化同步给两者，不静默替换已确认范围。
- **文档最少包含：**目标与使用者、范围与非目标、主要行为和必要接口/约束、边界与失败行为、可逐项核对的验收清单及验证方式、未决问题、确认状态与依据。验收项可用 `AC-1` 等编号供实现和 review 引用。未确认的部分标为草案或待决定；已在对话中明确确认的内容记录确认依据即可，不为落盘重复索取确认。向用户报告实际保存或复用的文件路径。

### 开发基线

- **新模块必须新建工作树：**Git 项目开始一个新模块的开发时，主 agent 必须先为它新建专用工作树和模块分支，记录其绝对路径 `MODULE_WORKTREE`、分支和 `BASE_SHA`，再开始实现。不能直接在主仓库或其他模块的已有工作树中开发新模块。只有续接同一个已开始的模块，才复用该模块记录中的工作树和分支。整个模块的实现、自测、集成、review 修复、复审和最终验证均使用该工作树及同一模块分支；不按子任务、开发者、阶段或会话另开开发工作树，也不回主仓库继续实现或审查未交付的模块。遵循项目目录和分支规则，项目未规定时默认主仓库 `.worktree/<模块名>/`；仓库内隔离目录先检查 Git 忽略规则，仅在确有缺失时补充。不切换运行服务目录的分支，不为模块之外的无关小改动机械创建工作树。
- 记录实际工作目录、分支及整个任务起点 `BASE_SHA`。未提交内容不会自动进入新工作树；核对必要源码和文档基线，不擅自 stash、覆盖或丢弃。共享文档使用同一绝对路径和内容哈希或提交版本；复制后核对内容一致。
- **非 Git 项目：**记录实际模块开发目录 `MODULE_DIR` 和可核查的文件快照基线，分支与 `BASE_SHA` 标为不适用，不虚构 Git 工作树或 SHA。后文及角色指令中的 `MODULE_WORKTREE`、模块分支和 Git 差异要求，分别对应这个固定模块目录、无分支及快照比较；实现、审查和续接使用同一模块目录。
- 普通功能和复杂模块修改前，运行与影响范围相关的现有测试，记录执行目录、代码状态、必要环境条件、命令及通过/失败摘要，作为测试基线。主 agent 可统一获取基线，开发者复用与自己范围及环境一致的记录；小改动按风险选择针对性检查。没有适用测试或环境无法执行时明确记录缺口，不虚构干净基线。
- 判定“历史失败”需要修改前的记录，或在隔离的原始基线上复现；仅凭错误看起来无关不能归为历史问题。未证实的失败标为原因未明，保留已知失败对验收的影响，继续不受影响的工作；关键验收仍受阻时不能宣称完成。

## 3. 开发分工

普通功能默认由主 agent 或一个开发 agent 连续实现，再交一个独立 reviewer。复杂模块按独立边界增加开发者：接口稳定、写入所有权不重叠、能够独立推进时才并行；耦合紧密时顺序执行或交同一开发者。所有开发者共享 `MODULE_WORKTREE`，按文件或模块划分写入所有权；会互相影响的测试、构建和 Git 操作由主 agent 协调顺序。reviewer 以同一工作树的稳定版本为审查对象，审查期间暂停相关写入；独立性来自职责和上下文，而非另一份开发工作树。并行数由有效分工和当前工具容量决定，没有固定配额。

主 agent 维护全局上下文和按需的进度记录，明确每个任务对应的验收项。开发者自己测试，不默认再分出只负责跑命令的 tester。每位开发者可以连续完成多个任务并承担原任务修复；子 agent 不再成为调度器。

### 进度与续接

复杂模块或需要跨会话交接的任务，把进度和证据写入已有计划的进度区；没有合适记录时，按项目约定保存，缺省使用权威需求文档同目录的 `progress.md`。记录任务与验收项、实际工作目录/分支、任务基线与当前代码状态、实现与验证及 review 状态、证据路径或提交、未决项和下一步。已有实现但验证或 review 待补时分别标明，不只写“完成”。

恢复工作先读取记录，并对照当前代码、文档版本和证据核实。已证实完成且仍适用的工作不重复派发；新增改动只补查受影响部分，证据缺失则补证据，不能机械重做整个任务，也不能只凭旧的完成标记跳过验证。

续接、替换开发者和 review 修复都复用记录中的 `MODULE_WORKTREE` 与模块分支，先核对其中的未提交内容。路径不可用时先定位原工作树和保存的状态，保留已有成果；不能直接从主分支新建工作树冒充续接。确需迁移时，先获得用户对迁移的明确授权，再完整保留当前提交、未提交文件和必要数据，核对迁移前后状态并更新记录，只保留一个继续开发的位置。用于测试原始基线的临时副本只承担验证，不作为第二个模块开发工作树。

### 角色提示词与派发

派发时只读取所需角色，提示词随本 skill 一起分发：

- [module-developer](agents/module-developer.toml)：实现、自测、自查、修复。
- [module-reviewer](agents/module-reviewer.toml)：先检查需求符合性，再检查代码质量，返回结论，不修改交付文件。

派发前读取 [本机 MCP 与角色路由](references/module-agents.md)。通过 `module-agents` MCP 的 `list_roles(project_root)` 解析本次项目配置：`custom` 使用 MCP + app-server；`inherit` 使用当前 Codex 原生子代理。项目 `.agents/module-agents/roles.toml` 中的模型、供应商和可选 `effort` 是路由配置来源，角色 TOML 提供职责和权限约束，不另行固定开发模型。修复与复审沿用原执行路径和 worker/agent 标识。

使用当前工具实际支持的参数；MCP 工具常带服务命名前缀。自定义角色缺少 MCP、凭据或供应商兼容性时明确报告，不静默回退到原生或其他模型。继承角色不能用独立 app-server 的默认配置冒充父会话设置；检查原生角色与全局子代理默认是否覆盖继承语义。首次派发均提供必要的独立任务上下文；如果使用通用原生子代理，复制角色指令并遵守相同权限约束，不把复制指令视为自动应用了模型或沙箱配置。

首次派发 reviewer 使用独立上下文，不继承实现者的完整会话；使用 `collaboration.spawn_agent` 时设 `fork_turns="none"`。开发者也仅接收完成任务所需材料。复审可续接同一 reviewer，修复可续接原开发者，独立性不要求每轮重新创建进程。没有子 agent 能力时继续可完成的实现和自查，但明确独立审查缺失，不能把自查写成独立通过。

派发内容是一份任务说明：

| 项目 | 传入内容 |
| --- | --- |
| 要做什么 | 用户要求、任务范围、确认文档路径/版本或明确的简短需求、验收项及确认变更 |
| 在哪里做 | 模块工作树绝对路径 `MODULE_WORKTREE`、模块分支、项目规则、允许修改的文件/模块、依赖接口；开发者和 reviewer 均使用同一模块工作树，明确并非独自在代码库工作，不回滚他人改动 |
| 如何验证 | 实际存在的检查命令、代码与测试基线、当前代码版本、已执行结果及未验证项；明确开发者的模块回归和主 agent 的集成验证范围 |
| 审查追加 | 整个任务的基线至当前版本、暂存/未暂存变更、相关未跟踪文件、目录外的交付文档、验证证据；实现报告只作线索 |

不要把整个设计复制到每次派发中；提供可访问的权威文档与本次职责即可。材料较多时传入任务说明、验证报告和完整差异的文件路径，消息中保留本次范围、依赖接口、必要上下文及返回要求。不能用“实现者已确认正确”等结论引导 reviewer，也不预先限制问题严重度；用户已接受的例外按事实提供依据和影响，不改写成已修复。

## 4. 实现与集成

开发者先理解现有接口，完整实现分配范围，并完成必要的行为、边界、失败路径测试和自查。测试顺序由项目规则和改动风险决定，未采用 TDD 本身不是缺陷；可逆的文案等小改动采用针对性检查即可，不写只复述实现的测试。

测试按阶段安排：开发迭代时运行直接覆盖当前改动的针对性测试；开发者交回前运行分配模块的相关回归及项目要求的检查；主 agent 集成后验证跨模块接口和关键组合路径，并按影响范围执行项目级回归。遵守项目明确的全量检查要求，但不默认每次微调都跑全量。版本和环境仍适用的结果可以复用；修复或集成改变了被验证的路径时补跑相关检查。

对能稳定复现的 bug，先用最小回归用例确认原行为失败，再修复并确认同一用例通过，记录命令与关键失败/通过结果。已先完成修复时，在隔离副本中验证用例能捕获原始缺陷，不为补证据恢复或覆盖当前工作目录。失败应来自目标行为，语法错误或环境缺依赖不算复现。暂时无法稳定复现时记录尝试、证据与限制，继续定位；不编造失败记录，也不将此规则推广为所有新功能强制 TDD。

测试断言应覆盖需求中的可观察行为。mock 用于隔离外部、慢或不可控依赖，保留被测核心逻辑；检查替身是否保留当前路径依赖的数据字段、错误语义和副作用，避免因替身与真实契约不一致造成虚假通过。调用次数或参数断言适用于明确的交互契约，不能单独替代返回结果、状态变化或错误处理等行为证据。不为方便测试给生产代码增加仅供测试的业务接口。

遇到失败先收集证据、定位原因，再实施修复并验证，避免猜测式连续改动。跨组件问题沿输入、配置和状态追踪偏离发生的位置；每次实验验证一个可证伪的假设，尽量只改变一个变量，用结果决定下一步。区分本次回归、已有失败、未执行与环境限制，不通过放宽验收或隐藏错误获得通过。同一问题连续多次修复无效（例如三次），或每次修复都引出不同的新症状时，暂停继续打补丁。开发者向主 agent 提交复现、已尝试假设、修改与结果，由主 agent 重新检查根因、依赖和设计假设，确定有证据支持的下一步；主 agent 自己实现时同样先重新评估。只有涉及需求、范围或产品取舍的变化才交用户决定，不把每次技术排查变成审批。

多个开发者完成后，主 agent 检查实际差异并集成，重点核对共同接口、数据模型、错误语义、配置、迁移及调用链。各部分分别通过不能替代组合后的验证；代码冲突和接口漂移由主 agent 协调后解决。只有整合后的稳定版本进入整体审查。

## 5. 独立审查与修复

由未参与实现的 reviewer 检查整个功能，按顺序完成下面两类 review，并分别给出结论。一个独立 reviewer 完成两类检查即可，不机械拆成两个审查角色。

| 审查 | 对照依据与检查内容 | 输出 |
| --- | --- | --- |
| 需求实现 review | 对照权威需求文档或小改动的明确用户要求，逐项核对验收、目标行为、范围、接口、边界和失败路径；检查遗漏、误解及擅自扩展，不能只看开发者报告或测试通过数量 | `Spec Compliance`：PASS / FAIL / INSUFFICIENT_EVIDENCE |
| 代码质量 review | 检查实现逻辑、错误处理、状态与并发、数据和 API 一致性、安全边界、兼容与回归风险、复杂度及可维护性 | `Code Quality`：PASS / PASS_WITH_ISSUES / FAIL / INSUFFICIENT_EVIDENCE |

两类 review 都要核查测试与验证证据：是否覆盖需求和真实行为、mock 是否掩盖问题、结果是否对应当前版本、集成路径是否得到验证。验证是审查依据，不另设必需的第三个 reviewer。GrillMe 在前期澄清或质疑需求与方案，不能代替实现后的这两类 review；review 中出现新的产品取舍时由主 agent 按第 2 节处理。

审查包括 `BASE_SHA..HEAD_SHA` 的全部任务提交、暂存/未暂存差异、任务相关未跟踪文件和交付文档。`HEAD~1`、某一个开发者的补丁或普通 `git diff` 都不能单独代表完整范围。保持审查版本稳定，发生变化时记录新版本并补查受影响部分。启动审查不等于审查完成。

reviewer 只返回有证据的问题，允许无问题通过。主 agent 核实反馈，将有效问题交回原开发者修复并复测，再由原 reviewer 复审修复与受影响路径。reviewer 不修改代码后再自审。新增实质改动纳入审查；有据撤回错误反馈，需求或产品取舍争议才交用户决定。

计划与示例本身也属于审查对象。“按计划实现”不免除代码质量检查；区分实现偏离需求和方案本身存在缺陷，按实际影响处理。若修复会改变用户已确认的产品取舍，说明冲突并取得该变更的决定；不因此暂停无关修复。

- **Critical**：严重功能、安全或数据风险，必须解决。
- **Important**：实质需求缺失、回归、质量或关键验证问题，交付前解决；已有用户明确接受的例外应记录影响，不能写成已修复。
- **Minor**：不阻塞正确性的可选改进，按范围决定是否处理。

## 6. 验证与交付

主 agent 核对验收项、完整差异、实际验证结果和审查结论。按影响范围运行项目已有的相关测试、类型检查、构建、lint 或集成检查，不编造不存在的命令，不使用线上数据或真实外部服务做未授权验证。复用仍适用于最终代码的已执行结果；有新改动、失败或证据缺口时补充验证。

完成意味着确认范围已实现，所需验证有当前版本的证据，按所选流程要求的独立审查已完成，Critical 已解决，Important 已解决或有用户明确接受的例外。实现者报告和 reviewer 批准都不能替代证据；关键证据缺失时报告限制，不能声称完成。

交付简明说明：行为变化、验收与验证结果、适用的 review/修复结论、剩余限制，以及实际工作目录和分支（涉及隔离开发时）。复杂任务更新续接记录，保留文档版本、基线、进度和未决项。提交、推送、合并、部署及清理按用户授权与项目规则执行，本 skill 不额外授予权限。
